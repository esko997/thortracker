# Mixer ceilings: capability and implementation proposal

**Status: design for user review, not an implemented feature.** Source baseline: `73b2597` (0.38.0 candidate), inspected 2026-11-10. This document changes no player, project format, effect, exporter or UI. No builds, tests, reference renders or hardware experiments were run for this pass. Capability judgments below are source/hardware analysis, not acceptance-test results.

## 1. What is decided, and what is not

**User decision:** a ceiling is `effective = min(programmed level, ceiling)`, **not** multiplication by a gain. Automation below the ceiling is unchanged; higher automation flattens. Existing volume effects keep their meanings. The current assignment is the design/capability pass; it does not authorize implementing the recommendations below. Touch-only controls, original synthesis and synth panels remain outside this proposal.

**Principal finding:** a common-looking control cannot promise the same operation on every chip. Several chips have a writable level; others have an autonomous envelope, an attenuation control, a shared master, or sample data in the apparent volume register. A native export contains registers or a real driver, not Thor's emulator internals. A clamp added only inside an emulator is not automatically exportable.

**Recommended product boundary:** begin with a **programmed-level ceiling**, applied after the backend's existing software volume composition, before register encoding. Label its actual domain and limitations. Do not call this a compressor, audio peak limiter, or universal envelope ceiling. Where the user expects the *instantaneous autonomous envelope* to flatten too, that is a different, often nonportable requirement: mark it unsupported rather than substitute attenuation. Section 10 explicitly asks the user to choose this boundary.

These distinctions are substantive:

- For a software envelope producing levels `[3, 9, 15, 7]`, a ceiling of 10 produces `[3, 9, 10, 7]`. A gain of 10/15 produces approximately `[2, 6, 10, 5]` instead.
- If an existing player computes `P = compose(instrumentEnvelope, rowVolume)`, clamp **P**, not each input and not just `rowVolume`. In general `min(E * V, C)` is neither `E * min(V, C)` nor `min(E, C) * min(V, C)`.
- A hardware ADSR continuing below a capped FM channel-volume setting is still multiplied/attenuated by that setting. That is a ceiling on the *programmed control*, not `min(instantaneous ADSR amplitude, C)`.
- A cap before a nonlinear chip mixer is not a cap on final PCM. Several voices can still add, interact or clip. Preserve all existing headroom, DAC curves, filters and board balances; do not repurpose the SCC headroom fix or host output volume.

## 2. The proposed level domain, including “70%”

### Recommendation: native level first, percentage only as a named coordinate

The authoritative value should be the backend's named native **control domain**, not a floating-point universal gain. Show e.g. `Ceiling 10/15`, `Ceiling 88/127 — FM channel level`, `Wave ceiling 50% — hardware shift`, or `Master ceiling 10/15 — all SID voices`. Explain that these are not equivalent loudnesses.

If the UI offers “70%”, this proposal defines it as follows, pending approval:

1. For an increasing integer programmed-level domain `0..M`, choose `floor(70 * M / 100)`. Thus 0..15 gives 10, 0..31 gives 21, 0..63 gives 44, and 0..127 gives 88. Show the realized native value next to the request. It means **70% of the control range**, not 70% of pressure, perceived loudness, DAC amplitude, or full-scale PCM.
2. Attenuation registers are inverted into the backend's increasing level domain before comparison. Never apply `min` directly to attenuation: a *larger* attenuation value is quieter. Preserve the backend's existing mapping and reserved/mute codes when encoding back.
3. Controls explicitly defined as discrete gains use their actual available gains, not their register-code order: GB wave `{0, 25%, 50%, 100%}`, WS voice `{0, 50%, 100%}`, WSC Hyper Voice `{off, 12.5%, 25%, 50%, 100%}` in the currently used scaling mode. A requested 70% ceiling realizes 50%. An already programmed 25% stays 25%; 100% becomes 50%. Apply the cap **after** the existing effect-to-gain mapping so the old thresholds retain their meaning.
4. A 100%/default entry is a true bypass, including when a register has a nonzero minimum, an unusual mode or no ceiling support. Old songs must not take a new audio path merely because a default object exists.
5. Zero means the minimum of the specified control domain, **not universally mute**. FM maximum TL is finite attenuation, GB NR50 zero still amplifies by 1/8, and DC/output transients may remain. Do not key-off/retrigger or set a host mute bit to manufacture a universal zero endpoint. Use a separately named mute command with its separately agreed semantics.

For nonlinear chips this choice matters dramatically. In the present OPM/OPN/YM players, a channel level of 88 instead of 127 adds 39 TL steps; at 0.75 dB/step that is **29.25 dB** of attenuation before TL saturation, not the 3.10 dB associated with an amplitude factor of 0.7. AY/YM2149's measured DAC tables and SN76489's attenuation ladder are likewise not linear percentages. The UI must not display a bare `70% volume` and imply otherwise. [H2, H4, H5]

**Alternative requiring an explicit decision:** a normalized-amplitude ceiling could use a per-chip transfer table and round downward to the loudest realizable amplitude no greater than the target. This gives different results (SN76489's 2 dB steps put a 70%-amplitude request at about 63.1%, or −4 dB). It would require defined reference conditions for AY variants, FM carrier/patch composition, pan and shared nonlinear mixers. It still would not be perceived loudness or solve autonomous envelopes. Do not implement this alternative by changing the meaning of existing `Cxx`/volume slide/envelope values. If chosen, version the *new ceiling domain*, leaving effects untouched.

### Pipeline contract

For a supported ordinary lane:

`existing row/effect state -> existing software envelopes and composition -> programmed P -> min(P, C) -> existing pan / register encoding -> native chip -> native mix/filter -> resampler -> host output`

- Keep the uncapped automation accumulator, slide fraction, software envelope position and release state. A ceiling change never writes back into them. Raising the ceiling restores the value the original automation has reached, not a damaged/capped accumulator.
- Backend-specific rounding stays where it is today; clamp its resulting native control, not a newly approximated float version.
- Normally clamp a mono programmed level before pan. Where a chip exposes only composed L/R amplitude registers (SAA1099, WS wave), define the ceiling as **per-side amplitude limits** and disclose that saturating one side can change the balance ratio. Do not silently multiply both sides by a gain to preserve the ratio. A linked pre-pan alternative is a separate UI/domain choice.
- Hardware mode/ownership decisions are computed from original programmed state, not from the capped level. In particular, AY ownership, POKEY reservation/release, and sample completion must not change because a ceiling produced zero.
- Do not clamp waveform samples, FM modulators, oscillator frequency, PWM width, pan routing, DAC bias or shared master volume as a substitute for an unavailable lane level.

**Legend (proposed feasibility, not shipped support):**

- **E** — exact `min(P,C)` for a ceiling chosen in the stated native domain; no extra quantization beyond existing playback.
- **Q** — exact clamp to a representable level after explicitly downward-quantizing the requested ceiling. This does not promise exact analog amplitude.
- **R** — restricted mode/domain, shared resource, or driver/format constraint; read the condition.
- **U** — unsupported for that meaning/path without changing sound semantics or extending the format/driver contract.
- **—** — no native file export registered. `.thor` and generic `.wav` remain available for every system.

Preview/WAV entries deliberately describe **hardware-representable programmed-level controls**. An emulator-only instantaneous-envelope clamp is not quietly included in an E/Q entry. ### Why the restrictions are not implementation inconveniences

**Autonomous envelopes.** GB increasing envelopes can grow past a capped initial value; even decreasing envelopes are shifted downward rather than flattened if their initial level is reduced. Writing NRx2/retriggering changes envelope/phase behavior. AY/5B/OPN SSG volume registers select either a fixed level or the shared envelope: they do not contain `min(envelope,limit)`. VSU EV0 writes reload a level and SxLR multiplies it. SAA envelope amplitude has a PDM lookup and reduced amplitude resolution. FDS supports a real envelope but the current FamiStudio route uses direct gain. These must be checked by **mode**, not by chip name alone.

An emulator can potentially clamp a hidden envelope result while leaving its state running (GB/binjgb, AY, VSU, FDS, SAA, SID/reSID). That would require a separately approved **Thor-only** mode with waveform/DAC/filter placement specified and native-export refusal. Writing a sampled replacement envelope into a VGM is not automatically equivalent: timing resolution, register side effects, chip clock vs 44.1 kHz waits, CPU-driver budgets, YM's 32 EG levels vs 16 fixed levels, and loop phase can all prevent exact reproduction. This proposal does not authorize that conversion or call it exact.

**FM.** The owned OPL3/OPM/OPN/YM players already make volume changes by adding attenuation to the current algorithm's **carriers** only. Preserve that arrangement. A ceiling on their channel control should use the uncapped `vol8 >> 3`, clamp it, then run the existing `tl_out` calculation. EPSM/VRC7 instead have FamiStudio software volume composition and lookup tables, so use *their* post-composition boundary, not the OPM formula. Do not clamp every operator TL: a modulator controls timbre. Do not independently flatten the resulting carrier TLs unless explicitly designing a different feature: that changes carrier balance, and unequal base TL saturation already makes a common volume adjustment imperfectly uniform. All algorithms, additive carriers, 4-op pairs, borrowed chord voices, OPM noise, FM3 special pitches/CSM, custom OPLL patches and rhythm-nibble sharing need separate cases. A chip's internal EG, key scaling, AM/LFO and release continue; no claim that their quieter instantaneous portions remain identical under an attenuated carrier.

**SID.** There is no independent voice-volume register. Sustain is not an attack cap: attack still reaches its peak, and editing sustain/ADSR changes the instrument. D418 is one shared master after the three voices/filter, not a lane fader. Gate-off, TEST, waveform removal, sync/ring changes, filter-routing changes or reSID `set_voice_mask` are not native per-voice ceiling implementations. Filtering is shared and can be nonlinear; attenuating one voice before it can alter the filter response experienced by others. If a future Thor-only per-voice EG clamp is desired, explicitly define its location before the shared filter and preserve oscillator/sync/ring state. Do not advertise isolated stems or export parity from it.

**PCM.** Distinguish a level *control* from a sample's signed excursion. OPNA ADPCM-B and PCE DDA have useful level registers. MMC5 software PCM already has a gain control around DAC centre 128; clamp that control, not the waveform. YM PCM kit levels are baked before XGM2 mixing, so applying a cap requires appropriately selected sample variants, not scaling the final DAC stream. POKEY volume-only and TED D/A write waveform codes into apparent volume fields; clipping those codes changes waveform/DC and violates the requested control ceiling. WS CH2/Hyper Voice have discrete hardware gains; sample-byte rewriting is unnecessary for those gains and would be a separate resampling/baking feature. NES DPCM delta output/direct load is not a programmable amplitude gain; changing $4011 also changes the nonlinear TND mix.

**Shared modes.** Never use ceiling zero as a way to release ownership. Silent sources may clock SN noise, PCE LFO, POKEY high-pass/joined counters or SAA envelopes; SCC may share wave RAM; OPL3 may allocate pairs/chord voices; DMA/FM6 can be owned by a sample stream. Those effects must continue as they do with the original programmed song. The capability result must identify a logical owner/group, not merely offer one enabled slider per physical register.

| Mega Drive `.vgm`, `.xgm`, `.xgc` | `system/ym2612/YmExport.kt`; `ym_vgm.c::{ym_render,ym_export}`, `ym_xgm.c`, `YmPcmLowering` | Audit both routes: VGM records the real XGM2/Z80 machine writes, whereas XGM2/XGC build encoded frame/sample-bank streams. Apply control changes before both diverge. Preserve bank capacity, signed sample format, loop prefix, FM3 mode and PCM priority/ownership. |
| AY `.vgm` | `AyVgm` -> `ay_vgm.c::ay_vgm_render` -> `ay_player_tick` | Cap supported direct-level writes in the player; no hidden `ay_psg`-only clamp. |
| OPL3 / OPM `.vgm` | `Opl3Vgm` / `OpmVgm` -> `o3_vgm_render` / `om_vgm_render` -> `o3p_tick` / `omp_tick` | Log carrier TL generated by the changed player; loop register restores must contain capped values, not just sequential ticks. |
| OPN / OPNA `.vgm` | `OpnVgm` -> `opn_vgm.c::opn_vgm_render`, `opnp_tick` | Preserve matching-state loop detection, shared SSG restrictions, ADPCM-B memory data blocks and externally supplied rhythm ROM. |
| PCE `.vgm` | `PceVgm` -> `pce_vgm.c::pc_vgm_render`, `pcp_tick`, `pcp_timer` | Same level control in tick and sample timer execution; keep existing timer scheduling and sample bytes. |
| POKEY `.vgm` | `PokeyVgm` -> `pokey_vgm.c::pk_vgm_render`, player plus chip/timer IRQ execution | Include owner selection, timer-driven sample writes and the explicit sample-domain restriction. |
| SCC / SCC+ `.vgm` | `SccVgm` -> `scc_vgm.c::sc_vgm_render`, `scp_tick` | Clamp volume writes only; shared wave/test state and loop restore remain unchanged. |
| SAA1099 SAM / CMS `.vgm` | `SaaVgm` -> `saa_vgm.c::sa_vgm_render`, `sap_tick` | Preserve per-chip resources and address-write envelope clocks, including repeated writes that are semantically meaningful. |
| VSU `.vgm` | `VsuVgm` -> `vsu_vgm.c::vb_vgm_render`, `vbp_tick` plus `vsu_run` | Mode-aware restriction; loop equality includes autonomous chip state. Never add periodic EV0 reloads merely to approximate clipping. |
| WS / WSC `.vgm` | `WsVgm` -> `ws_vgm.c::{ws_vgm_render,run_tick}`, player/timer/DMA | Preserve realizable voice gains, sample timestamps and state-based loop points; keep Hyper Voice refusal in both Kotlin and native validation. |
| TIA NTSC/PAL, VIC, TED | `exports = emptyList()` in `TiaSystem.kt` / `CbmSystem.kt` | Do not invent a native file format or claim VGM support as part of this feature. Project and WAV only. |

**Export refusal is part of the feature, not a warning after data loss.** Resolve capabilities against the *whole played arrangement*, held notes, future mode changes, jumps and loops—not only the current row/instrument. Name system, lane/mode, first offending location where available, format and remedy. No silent bypass, best-effort attenuation, dropped sample channel, overwritten effect slot, instrument truncation or fallback to host PCM gain. A file export must not partially publish a failed result. Saving the editable project may remain possible under the existing structural-vs-export-error distinction.

A bounded exact bake may eventually cover some source-format cases; it must preserve raw user data and operate on a derived representation. Repeated patterns can enter with different volume/slide/envelope/shared state. Cloning an instrument once per ceiling or clipping only explicit row effects is not a proof. Report capacity expansion and refuse if timing, state or format limits prevent equivalence. This proposal does not promise an all-song baker.

## 5. UI, persistence and editing proposal

### UI

- Add a controller/keyboard-accessible **Mixer ceilings** surface reached from Song, with one row per supported logical lane plus explicitly named shared-master groups. Reuse `SongSetting`/existing menu and edit gestures rather than introduce touch-only panels.
- Each row shows the domain, programmed ceiling, realized discrete level, and capability: e.g. `SSG 2 — hardware envelope: unsupported`, `SID master — all 3 voices`, `CH2 voice — 50% (requested 70%)`, or `FM 1 — channel control only; ADSR not clipped`.
- Unsupported rows remain visible with a reason, not fake working sliders. A mode change can invalidate an existing nondefault ceiling; preserve the edit and show the error rather than erase the ceiling or alter the new instrument. Bypass/reset restores unchanged behavior.
- No new volume effect code and no rewriting existing `Cxx`, slides, instrument programs or global effects. Do not present per-pattern mixer automation in this slice; recommend song-wide fixed lane/group ceilings initially.
- Use ordinary fine/coarse increments in the native domain, and Reset to bypass. If percentage entry is approved, always show its resolved native step. A genuine meter would need uncapped/effective telemetry and is not required; do not label a static cap value as a measured output level.

### Data and persistence

Recommended shared song data is an immutable sparse collection of nondefault **target + domain + integer ceiling** entries. Targets are stable logical lane IDs for the song's registered system, or an explicit shared group such as `sid-master` / `vic-master` / `ted-master`; they are not transient physical operator indices or instrument slots. The implementation should first add stable lane descriptors where needed rather than save UI labels as identity. Store the resolved native limit (and a domain/version identifier); optional requested-percentage display data must not become a competing source of playback truth. Bypass is absence, not a maximum written through new code.

`Song` currently contains no mixer settings; `ProjectCodec.SongFile` is a strict envelope with global version 10 and independent backend versions. Add one coordinated project migration when implementation is approved (do not reserve a version number in this proposal; use the integration baseline then current). Older files get an empty collection. Reject duplicate targets, unknown target/domain, negative/out-of-domain integers and mismatched system identity structurally. Mode-specific export/playback incompatibility is a separate actionable capability problem, so a work-in-progress project can be saved and corrected. Never silently migrate a control-range percentage into an amplitude percentage.

Copies and Save As retain ceilings. Pattern duplication does not copy song-wide controls into cell data. Switching to a different system through conversion requires a visible conversion report: retain only semantically compatible target/domain mappings, and require acknowledgment for removal or quantization; no slot-index coincidence mapping. Undo restores the original conversion snapshot. New/open document resets to that document's ceilings. Workspace preferences and pane snapshots are not the song's audio truth.

### Live changes, Undo and mute interaction

Use `EditorSession.apply` and the existing gesture grouping/Undo history. One continuous adjustment is one Undo entry; no-op writes do not create history. An audio-affecting ceiling edit increments ordinary `documentVersion`, **not** document-replacement `documentGeneration`. Existing `onSongChanged`/image publication remains the integration seam.

For owned C players, carry resolved caps in validated image state and preserve `ChipEngineOps.apply_image`'s transport contract. Resolve tables/targets off the audio thread. At a documented next player tick, recompute the effective outputs for held and releasing voices without retriggering, resetting a sample position, corrupting an uncapped register shadow or allocating in the callback. Both capped and raw state must be distinguishable: after lowering then raising a ceiling, deduplication must emit the newly restored level even if no row effect changed. A seek/start/restart/audition/loop restore must initialize the same cap state. Lowering a ceiling can click on real chips; do not hide that by adding a smoothing gain or new timing semantics.

Capabilities must include **live applicability**, not just offline realizability. GB envelope updates and YM baked PCM are examples where an exact static conversion does not establish immediate held-note edits. Until a transparent live strategy exists, show the restriction and refuse that live operation; do not silently defer to a future note while claiming immediate feedback. This constraint may keep these modes out of the first implementation stage.

**Pattern mute has been deferred by the user after reviewing native-export incompatibilities; its companion work is a feasibility document, not a feature implementation.** Coordination considered pattern-local muted lane indices and an output gate while state continues, but native-file parity is unresolved, especially UGE and SID. Do not advertise that proposal as implemented or approved. A ceiling is not a mute, and no ceiling should change monitoring mute state. If a future pattern output gate is separately accepted, calculate the ceiling normally and let the gate suppress only its specified contribution; unmuting resumes at the current uncapped automation/envelope state through the current ceiling. No ownership transfer or shared-resource freeze merely because a lane is muted/capped. Any future combined export must check both features' restrictions independently. Mixer design decisions do not block the current release, zoom or documentation-site work.

## 6. Backend integration recommendations

Avoid a universal float fader in `TrackerAudio`, `audio_engine.cpp` or the host render loop. Extend `SoundSystem` with a small capability description/query (proposed, not an existing API) reporting target, domain/steps, scope, current-mode restriction, live applicability and each format's realizability. Compute whole-song feasibility when editing/exporting, not in the audio callback. A human-readable restriction should be produced from the same result the exporter enforces.

For owned C players, insert an integer clamp at the already identified resolved-level writer. Include image validation/versioning, lowering and native snapshots together. For the real-CPU drivers, plan explicit driver/data changes or bounded source-format baking; do not sneak a bus-write rewrite into preview and forget NSF/UGE/assembler files. Default/bypass images should continue down the old path. Use fixed-size per-lane storage bounded by the registered layout; no per-sample allocations, channel-name lookups or repeated transfer-table construction.

Preserve all original source instrument/effect data. Software slides and envelopes keep advancing past the cap. Keep waveform, register and oscillator state equal except for the intentionally changed level-control writes and their physically consequent chip output. In shared/nonlinear modes, audible effects on other channels are a real consequence to disclose, not a reason to synthesize isolated mixes.

## 7. Meaningful verification plan (not executed here)

1. **Clamp vs gain:** use `[0,3,9,10,11,15,7]` at cap 10 and require `[0,3,9,10,10,10,7]` at the actual register/control boundary. Independently compose envelope and row automation, including old rounding/minimum-one rules; catch an implementation that clamps an input rather than the result.
2. **Hidden state:** slide above cap, hold, slide below, raise cap while held, OFF/release, delayed notes and cuts. Compare uncapped envelope/slide/phase/owner state with the original player; only effective writes differ. Include apply-image relocation and shortened envelopes. Do not use nonzero PCM as evidence that a particular audition/edit was accepted.
3. **Identity/default:** existing demo and edge-fixture images, register traces, generated exports (with fixed date metadata) and WAV PCM remain unchanged with no settings or all bypass. Unsupported modes at bypass remain playable. Opening and resaving a project may change its version/metadata, but not its musical data or default audio.
4. **Discrete/nonlinear:** exhaust every legal native level and ceiling, require monotonic non-increase, exact equality below cap, and explicit downward quantization. Test GB NR32 register order; SN attenuation inversion; AY vs YM fixed DAC entries; PCE 31-level, FDS doubled/clamped gain, WS voice and Hyper Voice thresholds. Compare register/control semantics, not “70% RMS.”
5. **Autonomous-envelope adversaries:** GB upward/downward and envelope-pace changes; AY/S5B/OPN hardware shape and shared-owner handoff; VSU grow/decay/repeat; SAA internal/external clocks, inverted right envelope and PDM amplitude pairs. Require the designed refusal or exact supported-domain result. A test that merely sees a quieter attack is insufficient.
6. **FM:** every OPN/OPM algorithm, both OPL3 2-op algorithms and all 4-op connections, OPLL preset/custom/rhythm and EPSM tables. Verify all carriers (including chord copies) and no modulators change; preserve KSL/high register bits, patch identity, key/feedback state and release. Test saturation of unequal carrier TLs, noise, CSM and FM3 special mode. Explicitly demonstrate that channel-control capping is not instantaneous EG clipping.
7. **SID/shared resources:** test the shared master with changing filter-mode high nibble and master automation from every source; per-voice request refuses. Check sync/ring/filter state is not manipulated as a workaround. Exercise VIC owner changes, TED D/A entry/exit, POKEY joined/high-pass/two-tone with clock sources capped to zero, PCE LFO and SN tone3 noise.
8. **PCM:** require byte-identical source samples where a hardware control suffices; verify MMC5's DAC centre and actual gain control, YM lane-specific baked variants/full bank/held sample limitation and both export routes, OPNA ADPCM memory/looping, WS signed/stereo/DMA and existing Hyper Voice refusal. Reject DPCM and TED/POKEY waveform-code clipping masquerading as gain-control caps.
9. **Export parity:** independently parse/decode every accepted native format, play its real driver/register stream, and compare with the supported preview boundary through intro, first/second loops, speed changes, delays and state restoration. Source-format import/re-export checks must use the actual pinned upstream tool, not just compare our generated text. Refusal fixtures include filled effect columns, shared instruments at different caps, full tables/banks and prior-state-dependent repeated patterns.
10. **Product boundaries:** project migration, malformed entries, Save As, Undo/Redo grouping, replacement, pane swap, conversion reports, parked orders and mode changes. Start offline WAV, edit live ceiling, and prove the export snapshot remains fixed. Test Android and both Linux hosts through their actual image publication paths, then measure callback cost under existing workstation/build constraints.

The parent/integrator owns all execution. Existing relevant test areas include `core/src/jvmTest/kotlin/org/thortracker/backend/`, system model/editor tests and `app/src/test/cpp/` native player/chip/WAV tests. Extend their real behavioral fixtures; do not assert strings or API wiring as proof of audio semantics.

## 8. Staged implementation, gated by decisions

1. **Agree semantics and capability UI first.** Resolve section 10, including the percent domain, autonomous-envelope boundary, zero endpoint and shared-master controls. Establish explicit native-export refusal policy. Do not start with a slider that silently becomes a gain.
2. **Implement complete vertical slices on direct owned-player controls.** Good initial candidates: SCC/SCC+, TIA, direct AY mode and PCE's main channel level. Include project persistence/migration, Undo, capability/refusal reporting, preview, WAV, native VGM where registered, live image application and behavioral tests together. Mixed-mode songs must refuse unsupported caps, not bypass them. Make the UI honestly report other systems as unsupported until their stages land.
3. **Add stereo/discrete and shared controls deliberately.** WS wave/CH2 gains, SAA ordinary amplitude, OPNA rhythm/ADPCM-B and optionally shared VIC/TED/SID master controls. Keep hardware-envelope, TED D/A and Hyper Voice export restrictions explicit. Decide and test pan semantics before exposing stereo ceilings.
4. **Add qualified FM control ceilings.** OPL3/OPM/OPN/YM and VRC7/EPSM/OPLL only with reviewed carrier/domain wording, ownership and driver/export parity. They do not close an instantaneous-envelope requirement.
5. **Integrate real-CPU driver and editable-source formats.** NES NSF plus source-format refusals/bakes, Banjo source/VGM contract, GB static/wave subset and GoatTracker shared master. This stage has real data/timing/capacity constraints; no assumption that all editable formats can express every runtime ceiling. The complete feature may legitimately retain explicit unsupported cases after user approval.
6. **Resolve difficult sample/live modes separately.** YM PCM variant/lane selection and held-note behavior; any proposed POKEY sample-gain domain. Never alter sample data or invent a host postmix shortcut under the ordinary-level label.
7. **Only if separately approved: Thor-only envelope ceiling.** Specify core/DAC/filter placement per backend, performance and honest native refusals. This is not necessary to ship the reviewed portable subset, but the original request must not be described as universally fulfilled without the user's acceptance of that subset.

No stage silently removes a backend's existing fidelity or format support for unchanged/default songs. Each stage completes its enabled targets end to end; the list is not permission to ship nonfunctional controls.

## 10. Decisions needing user review

1. **Meaning:** accept a named programmed-control ceiling with the autonomous-envelope restrictions above, or require true instantaneous-envelope flattening too? The latter cannot be promised in every native format. This is the primary scope decision; implementing only the former without agreement would narrow the request.
2. **Units:** prefer native units with optional “% of control range” as proposed, or commission per-backend normalized-amplitude mappings? Never an unlabeled universal “70% loudness.”
3. **FM:** accept an explicitly labeled channel-control cap, or exclude FM until a separate envelope/output contract is chosen? Carrier TL attenuation is not the same as clipping the autonomous carrier envelope.
4. **Zero:** accept “minimum native control, not necessarily silence” and separate mute, or require a zero-is-mute extension with its own mode/export restrictions?
5. **Shared hardware:** expose clearly named SID/VIC/TED/shared rhythm master controls, or leave them unavailable rather than placing misleading per-lane sliders? They change all affected voices.
6. **Stereo:** accept per-side saturation where stereo registers are the level domain, or require a separately defined pre-pan linked cap? These cannot always preserve both exact side ceilings and the original balance ratio.
7. **Persistence/scope:** approve song-wide fixed lane/group ceilings first, separate from pattern-local mute; no extra effect automation in this pass?
8. **Portability:** accept explicit unsupported/refused native exports and mode-aware controls, or require every offered control to be available in all of its system's registered formats? If all-format parity is mandatory, defer affected source-driver systems until lossless realization is proven. Thor-only envelope processing must be opt-in and separately named if ever added.
9. **Live PCM/static subsets:** accept excluding modes without transparent held-note updates, or define a visible note-boundary edit policy? This cannot be silently chosen for YM PCM/GB envelope behavior.

**Proposed PLAN summary for the integration owner:** “Mixer-ceiling capability/design pass complete: `docs/MIXER_CEILINGS.md` inventories all 43 registered systems and every native export route. User-approved operation is min(programmed, ceiling), not gain. Implementation awaits review of level/percentage domain, FM versus autonomous envelopes, shared masters, stereo, zero/live behavior and native-format refusal policy. Begin only with reviewed end-to-end supported slices; retain explicit unsupported cases and unchanged default songs. No mixer feature implemented or runtime verification claimed.”
